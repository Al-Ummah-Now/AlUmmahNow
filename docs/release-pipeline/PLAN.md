# Release pipeline: plan

Implements [SPEC.md](./SPEC.md). Each phase is independently shippable. Each one leaves prod deploys working at least as well as before, and is merged only when its CI is green. Each phase has a GitHub issue labelled `queue`. Issue numbers are in the table below (`#n` = AlUmmahNow).

Order: auth first (smaller, deploys from CI today), then AlUmmahNow. Auth phases 1–4 and AlUmmahNow phases 1, 5 and 6 can run in parallel.

AlUmmahNow convergence comes early (owner requirement, SPEC §3.1): one codebase, with `main` as the only trunk.
- **C1** starts right after 1B.
- **C2** needs stage for web and api-videos, so the stage half of phase 7 moves ahead of C2.
- **C3** retires `integrate/qa-features` and `develop`.

AlUmmahNow order: 1B → C1 → 7 (stage, release workflow) → C2 → C3 → 5/6 leftovers → 8.

## Phase 1A: auth CI gates

Scope:
- `scripts/check-wrangler-config.ts` (SPEC §8). For now it checks `env.production` of auth (issuer, `ENVIRONMENT`, Secrets Store bindings, no test bindings, no localhost), plus profile, admin and audit-consumer prod configs. It flags any bare `wrangler deploy` in workflows and package scripts. Run in `test.yml` and as the first step of every prod deploy job.
- Migration checks (SPEC §6.2): append-only check for `apps/auth/migrations*/`, and a schema snapshot generated by applying `openauth migrate` + app migrations to a local D1.
- `/health?deep=1`: reports, as booleans only, that each required binding resolves (D1 query, KV get, Secrets Store secrets readable, queue bound) and the issuer value. `/health` stays cheap.
- Remove `develop` from triggers. Node 22. Pin `ubuntu-24.04` for Playwright jobs.

Acceptance:
- A PR that changes `deploy:prod` back to bare `wrangler deploy`, removes `RESEND_API_KEY` from `env.production`, or sets a localhost issuer fails CI. Proven by unit tests of the checker on fixtures.
- A PR that edits an existing migration, or adds one without updating the snapshot, fails CI.
- The prod deploy job runs the config check before `wrangler deploy`.

## Phase 1B: AlUmmahNow CI gates

Scope:
- `deploy.yml`: remove `continue-on-error` from tests. Run CI on PRs into `main` and `integrate/**`. Remove `develop` triggers.
- Fix or quarantine currently failing unit tests so the gate can be green. Each quarantined test gets an issue; there are no TODOs.
- `scripts/check-wrangler-config.ts` for the 6 apps: prod configs have prod routes and vars and no localhost, and every deploy command in workflows names an explicit config.
- Migration append-only check and schema snapshots for every D1 migrations dir.

Acceptance: a failing unit test blocks a PR. Editing an old migration fails CI. The prod config check runs in CI.

Prod impact: none. Prod deploy jobs are unchanged; #185 still applies.

## Phase 2: auth test sink, test-route lock, regression E2E

Scope:
- Email code sink (SPEC §9.2) behind four conditions, plus unit tests for every combination.
- All `/test/*` routes require `X-E2E-Secret`; otherwise 404. This fixes the unauthenticated `/test/debug/kv` on QA.
- Bind `E2E_CODE_SINK_SECRET` on QA (Secrets Store `_QA`).
- E2E helpers read codes from the sink when the address is `@e2e.alummahnow.net`. The Resend-API path remains for the single delivery test.
- New specs in `e2e/tests/release/`:
  - `signup-signin.spec.ts`: profile client and auth-admin client, sign-up → code → sign-in → session → sign-out → sign-in again (R1).
  - `forgot-password.spec.ts`: known email resets and signs in; unknown email shows the same "code sent" screen and no error (R3).
  - `send-code-failure.spec.ts`: the form stays visible with an error when sending fails (coordinate with the in-flight branch `fix/send-code-failure-stays-on-form`; do not duplicate it).
- Add the `release` specs to `qa-e2e.yml`.

Acceptance: QA E2E on the PR runs the new specs and they pass. A unit test proves the sink is off with `ENVIRONMENT=production` even when the secret is bound. Prod `GET /test/email/x` is still 404 (checked after the merge deploy).

## Phase 3: auth stage environment

Scope:
- Create stage resources: D1 `al-ummah-now-d1-stage`, KV `AUTH_STORAGE` stage, queue `audit-events-stage`, Secrets Store entries `*_STAGE` (salt, master key, Resend key, sink secret), analytics dataset `auth_events_stage`.
- `env.stage` in `apps/auth/wrangler.json` mirroring `env.production` (parity enforced by the config check). Same for profile, admin and audit-consumer. Hosts: `auth.stage`, `profile.auth.stage`, `admin.auth.stage`.
- Stage seed: openauth migrate + prod migration history, roles, and clients mirroring prod clients with stage redirect URIs, including a web client for `videos.stage.alummahnow.net`.
- `scripts/smoke.ts --env stage|production [--version-override <worker>=<id>]` (SPEC §7.3).
- `scripts/stage-deploy.sh`: manual deploy to stage, used until phase 4 lands.

Acceptance: `pnpm smoke --env stage` passes. The `release/` E2E specs pass against stage locally and from a `workflow_dispatch` run. The config check enforces stage/prod parity.

## Phase 4: auth release workflow

Scope:
- `release.yml` on push to `main` (SPEC §5.2): build once (`--dry-run --outdir`) → stage migrate + deploy + smoke + E2E → prod migrate → `versions upload` → `@0%` + override smoke → `@100%` → prod smoke → auto-rollback on failure → sync stage → release summary + manifest artifact (worker → previous/new version ids).
- `rollback.yml` (`workflow_dispatch`) and `pnpm release:rollback`.
- Remove the prod deploy jobs from `deploy.yml`, in the same PR that enables `release.yml`.
- Docs: CLAUDE.md, README, CICD.md, `docs/release-pipeline.md`.

Acceptance:
- A trivial change goes PR → CI → merge → stage → E2E → promote → smoke, with links in the issue.
- Rollback drill: run `rollback.yml`. Prod is on the previous version and smoke passes. Roll forward again.
- A deliberately broken smoke (on a throwaway branch, via `workflow_dispatch` with an injected failing check) triggers auto-rollback.

## Phase C: AlUmmahNow convergence (one codebase)

QA runs `integrate/qa-features` (177 ahead of `main`, 20 behind, 867 files). Prod runs `main`, deployed by hand. The owner expects one codebase. AlUmmahNowAuth already uses `main` for QA and prod, and stays as it is.

**C1: forward-port (now).**
- One PR into `integrate/qa-features` that merges `main`. Where both branches fixed the same thing (#188, #197, #205, the Bunny file-name and URL-field signing), keep integrate's version.
- Must arrive on integrate:
  - #209: sign-in `redirect_uri`
  - #214: profile loop, prod API CORS, quiet missing translations
  - legacy Bunny library URL signing (`40a5313`)
  - bulk-delete ownership (`380db16`)
  - Node 22 / `ubuntu-24.04` CI
  - Seed QA workflow registration
- Includes #212 (add-account `redirect_uri`) once it merges to `main`.
- From now until C3, every prod hotfix lands on both branches.
- Acceptance:
  - `git log integrate..main` is empty.
  - QA E2E plus the release regressions pass on integrate: R1 for web, R4, and the player job.
  - Each forward-ported hotfix's own test passes on QA.

**C2: promote integrate to prod through stage** (after phase 7's stage for web + api-videos exists).
- Prod data steps, rehearsed on stage first. Both are expand-only, run before the traffic shift, and stay if the code rolls back:
  - **Search D1 ownership index:** create the prod `SEARCH_DB`; apply `apps/api-videos/migrations/search/`; run `scripts/search-backfill.sh` (`POST /internal/search/backfill`) until it reports `complete`. Check: `complete` is true and the row counts match the bucket object counts.
  - **R2 translations:** seed with `translationsSync`. Check: every locale's object exists with the expected version.
- Release integrate's head through `release.yml`. Stage E2E must pass first: R1 sign-up → code → sign-in for web, profile and admin, R4, the player job, and the legacy suite's stage-safe specs.
- Promote at 0%, run the pre-traffic smoke, go to 100%, run the post-promote smoke. Rollback is ready, and the owner picks the window (SPEC §11.8).
- Then fast-forward `main` to the promoted commit.
- Acceptance:
  - Prod runs integrate's code.
  - `main` = that commit.
  - The prod smoke and the synthetic sign-in pass.
  - Both data checks are green on prod.

**C3: single trunk.**
- QA deploys from `main`: on merge, or PR previews for the apps that support them. Fix the dead `deploy-qa` job, which still keys on `develop`.
- Every workflow triggers on `main` only; the `integrate/**` triggers are removed.
- Default branch and PR base are `main`.
- Tag `archive/integrate-qa-features` and `archive/develop`, then delete both branches.
- CLAUDE.md, READMEs and the deployment docs describe one flow: PR → CI → QA → stage → promote.
- Acceptance: no workflow mentions `integrate` or `develop`, and the branches are gone (tags remain).

## Phase 5: AlUmmahNow web regression E2E and player

Scope:
- Unit: the authorize `redirect_uri` built by `login()` equals the one `/api/callback` exchanges with (also for multi-account) (R1).
- `apps/web/e2e/release/`: `signup-signin.spec.ts` (R1), `callback-errors.spec.ts` (R4). Targets come from env (`E2E_ENV`), codes from the auth sink.
- Player: a Playwright project with `channel: 'chrome'`, a VP9/WebM fixture, and no silent skip under CI (R5).
- Run on PRs into `main` against QA (and into `integrate/**` until phase C3).

Acceptance: specs run and pass on QA in CI. Reverting the #188 fix or the redirect_uri hotfix on a scratch branch makes them fail. The player spec reports "passed", not "skipped".

## Phase 6: AlUmmahNow data contracts

Scope:
- `packages/data-contracts`: schemas for R2 records (videos, channels, profiles, playlists, global-settings, translations) built from the existing shared-types zod schemas, a JSON Schema snapshot, and a CI snapshot check that requires a `data-migrations/` entry.
- `pnpm data:check --env qa|stage|production`: read-only sample-and-validate. Translations are checked against `messages/en.json`.
- `pnpm data:migrate --env …`: idempotent runner with a completion marker.

Acceptance: changing a contract without a data-migration fails CI. `data:check --env production` runs read-only and reports key names only. The first run's findings are filed as issues.

## Phase 7: AlUmmahNow stage + release

Scope:
- Stage resources for web and api-videos: workers, R2 `*-stage` buckets, D1 stage DBs where api-videos uses them, Bunny staging zones, stage auth client.
- `env.stage` / `wrangler.stage.jsonc` with parity checks. Web builds twice from one checkout (SPEC §4.2).
- `release.yml` for web + api-videos with the same shape as auth. `rollback.yml`.
- Cross-repo stage lock in stage KV (`release-lock`, 2h TTL), used by both repos' release workflows.
- Remove the old prod jobs for web and api-videos from `deploy.yml`.

Acceptance: trivial change through the full pipeline, rollback drill, and auto-rollback proven, as in phase 4.

## Phase 8: build-once web and the remaining apps

Scope:
- Move host-specific `NEXT_PUBLIC_*` values to runtime config served by the worker, so one web build serves stage and prod. Remove `NEXT_PUBLIC_BUNNY_API_KEY` and `NEXT_PUBLIC_ENCRYPTION_SECRET` from the client bundle (they are secrets).
- After #163/#185: bring processor, websocket-server, admin-api and admin-web into the pipeline with a one-time verified catch-up release.
- Quarterly rollback drill (scheduled workflow that opens an issue).

Acceptance: one web artifact deploys to both stage and prod. All 6 apps are released only through `release.yml`.
